Part 1

The requirement, as given

This is the brief exactly as the FDE receives it (it is “Project 3” in the brief; The Gen Academy's repository calls it 2C). Everything after it works backwards from these words to the system that was built (repository 2C-Graph-RAG-for-Organizational-Knowledge, commit b9bae00).

Project 3: GraphRAG for Organizational Knowledge

Description

Model your team’s or organization’s knowledge as a graph — people, projects, skills, documents, and decisions — and use GraphRAG to enable queries that traditional vector search can’t handle well. Think: “Who worked on the last compliance audit and what tools did they use?” or “What decisions were made about our pricing model and who approved them?” Build the graph with 20+ nodes, run queries against it, and compare GraphRAG results with traditional vector-based RAG on the same questions. This project highlights when structured relationships matter more than semantic similarity.

Best For

Program/Project Managers (organizational knowledge), Executives (decision tracking), Consultants (client engagement knowledge), Tech Leads (technical decision logs), Strategy roles.

FDE analysis: from the brief to the design

2C in one paragraph. A hand-written mock organization (data/mock_data.py) holds 32 nodes (7 people, 4 projects, 6 skills, 6 tools, 5 documents, 4 decisions) and 48 edges of 7 relation types, such as WORKED_ON, USED_TOOL, APPROVED and DECISION_FOR. The same data feeds two pipelines. Vector RAG turns each node into one short text chunk (its own attributes only), embeds the 32 chunks with OpenAI's text-embedding-3-small into a FAISS index, and gives gpt-4o-mini the top 8 for each question. GraphRAG is a LangGraph workflow over a NetworkX graph: an LLM call extracts entity names and relation types from the question (entity linking); the names are fuzzy-matched to node IDs (seeds); if none match, a regex and topic-keyword fallback tries instead; the graph is expanded two hops from the seeds in both directions, optionally keeping only the asked-about relation types; document text is attached; and gpt-4o-mini answers from the resulting facts. Six benchmark questions, Q1 to Q6 as in 2C's code (unrelated to the “Q3 2025” in a project's name), each have a gold set of strings a correct answer should contain; recall is the share of those strings found in the answer. Here “GraphRAG” means retrieval by graph traversal, close to the “local search” of Microsoft's GraphRAG. Microsoft's version also builds the graph from documents with an LLM and, for broad “global” questions, uses community summaries (LLM-written summaries of clusters of closely linked nodes); 2C does neither.

2.1How an FDE reads this brief

  1. Find the real deliverable. “compare GraphRAG results with traditional vector-based RAG on the same questions” and “when structured relationships matter more than semantic similarity” make the output a comparison and a rule of thumb. The comparison is only worth something if both sides get the same facts.
  2. Ask where the graph comes from before how to query it. In a real organization, people live in the HR system, project work in a ticketing tool, documents in a wiki, decisions in meeting notes and approval workflows. Building and maintaining the edges is most of the work, including entity resolution (at build time: matching “B. Martinez” in one system to “Bob Martinez” in another), which is different from entity linking (at question time: words in the question to nodes). 2C writes its graph by hand, which is fine for learning if everyone knows the hard part was skipped.
  3. Look at what each side can see. Before comparing answers, list the facts each pipeline's context can contain. In 2C none of the 48 edges reaches the vector index; only some document and decision text mentions related projects or tools (2.7).
  4. Test at the size the customer has. Retrieval has to choose only when the data does not fit in a prompt; below that, it matters for cost, citations and permissions, not for whether the facts can be reached. 2C's whole graph, with every edge and all document text, is about 7,100 characters; at that size the first control is to give the model everything.
  5. Org knowledge is people data. Who worked with whom, who has which skill and who approved what are personnel and possibly confidential records. Permissions, privacy and the line between knowledge sharing and employee monitoring come before the first demo.
  6. Score the claim, not the vocabulary. A name in an answer is not proof the system knew the relationship. Scoring must check that each named entity is correct and supported by the retrieved facts.

2.7Checking the comparison, as an FDE would

The brief's core is “compare GraphRAG results with traditional vector-based RAG on the same questions”. Before quoting a winner, check what each side could possibly see. In the engagement this design comes before any build (step 4 in 2.8); it sits here because it refers to the parts chosen in 2.5. All checks below are retrieval only: no answers were generated.

What the comparison cannot show

  • There is no published result. compare.py prints a recall table but saves nothing; the README and the solution kit report no numbers. In code
  • No graph edge reaches the vector side. Its 32 chunks hold each node's own attributes; none of the 48 edges is written anywhere, and each person's name appears only in that person's own chunk, so the 31 edges that involve a person are invisible to it. Some document and decision text does mention related projects or tools. For Q1, our proxy top 8 holds 5 of the 6 gold names; Drata and AWS Audit Manager are tied to the audit only by the audit report's prose (and, for AWS Audit Manager, a decision's rationale). An answer naming Alice and Frank as the audit team would be a guess from job titles, Okta would be unsupported, and substring recall would score all three as hits. Checked
  • A fairer index retrieves most of the missing facts. Adding the 48 edges as sentences (“Alice Chen worked on Q3 2025 SOC2 Compliance Audit (role: Lead)”) and retrieving the top 16, twice 2C's k, brings back every needed edge for Q1, Q2, Q4 and Q5, and all of Q2's and Q5's even at top 8. Q3, which needs 14 edges, stays hard (3 of 14). This uses a local stand-in for OpenAI's embedding model, and no answers were generated, so whether answers would close the gap is untested. Checked
  • Q3 is mostly out of GraphRAG's reach too. From Bob, project → teammate → skill is three hops. Two hops do reach Alice's AWS and David's Python, because Bob has those skills too, but not Machine Learning, Penetration Testing or SOC2 Compliance as a skill. The gold set asks for those three and omits the two that are in reach (perhaps reading “bring” as “add to Bob's”; the question should say so), and its “SOC2 Compliance” is a substring of the project name “Q3 2025 SOC2 Compliance Audit”, so naming the project scores the skill. Checked
  • At this size, full context is the control. The whole graph in GraphRAG's own format, with every edge and all document text, is 7,093 characters; the 32 node chunks alone are 3,919. From the fallback's seeds, an unfiltered 2-hop expansion returns 44–66% of the nodes and 2,768–4,312 characters, 39–61% of the whole; for Q1–Q5, the relation types an LLM would most likely pick (our assumption) cut that to 575–1,759. The solution kit rejects “LLM over the full dataset” because it does not scale, hides which facts were selected and skips testing retrieval. All true in production, but at 32 nodes full context is the ceiling every retrieval method should be measured against. Checked
  • The benchmark can't tell whether the LLM linker helps. The hand-written fallback alone links every question to the right project or person. Separately, the fuzzy matcher sends 5 of the 32 node names to the wrong node Checked: a latent bug the six questions probably never trigger, and one more reason to test linking on its own. Inferred
  • Substring recall is lenient and brittle at once. It counts a name whether or not the claim is right, ignores extra wrong names (no precision), and misses paraphrases (“no critical findings” fails “zero critical findings”; “three-tier” fails “3-tier”). Q5's gold is just “Snowflake”: naming it scores 100% however the answer was reached. Six questions, one run, no spread. In code

An FDE's version keeps the idea and changes the design (figure 11 draws the result):

  1. Build the graph from real sources, even a small slice, with provenance and dates on every edge, so the hard part is in the test.
  2. Give both sides the same facts. Run five set-ups on the same questions: vector over node text, vector over node text plus edge sentences, GraphRAG, graph queries (templates or text-to-Cypher), and the whole graph in the prompt as a control while it fits.
  3. Grow the data from a real export (one department's org chart, projects and wiki) until the full graph no longer fits or accuracy drops as the context grows; at 2C's density that is roughly 2,000 nodes for gpt-4o-mini's 128k-token window, fewer with real-length documents. Add ablations: GraphRAG with gold seeds (isolates linking), hops 1, 2 and 3, the filter on and off.
  4. Write 30–50 questions with users: lookups, lists, three-hop paths, time-dependent ones, questions with no answer, and questions the asker may not be allowed to see answered. Keep a third back from tuning the linker, the topic map and the prompts.
  5. Score entities, not words. Have each pipeline cite a node or edge ID for each claim and score the IDs, precision and recall; judge paraphrases by hand or with a judge model checked against human labels; measure linking accuracy on its own. With 10–17 held-out questions, report per-question wins and losses, not averages. Repeat runs and store every result.
  6. Give every failure one cause, the earliest stage that went wrong. 2C's kit proposes tracking which linking stage lost the context; this extends that to every stage:

2.10What to take away

  1. A head-to-head is only fair if both sides see the same facts. No graph edge reached 2C's vector index, so “vector search can't” is untested; in our retrieval-only proxy, edge sentences surfaced every needed edge for four of the five relational questions.
  2. The hard part of organizational GraphRAG is building and maintaining the graph: sources, edge definitions, entity resolution, provenance, time and permissions. Query-side cleverness can't fix a missing edge.
  3. Test at the size you'll run at. At 32 nodes the whole graph fits in a prompt with room to spare, and an unfiltered 2-hop expansion is already about half of it.
  4. Graph traversal earns its place on path questions, but only with enough hops: Q3 needed three, and neither side's context linked Bob's teammates to the skills its gold set asks for. We ran no LLM, and a model could still name them from job titles, which substring recall would count.
  5. Score entities and claims, not words: substring recall rewards guessed names and misses paraphrases.
  6. The rule of thumb to test: relationships beat similarity when the answer is a list, path, intersection or count over records (who worked on, who approved, tools two projects share), when the relationship lives in a system of record rather than in prose, and when each fact needs a source and a permission check. Similarity wins when the answer is in prose (Q6) or the question names things loosely. Real questions mix both, so production is usually hybrid: route by question type, or combine graph facts with retrieved passages (2C lists this as future work).
